# Baseline standard (fallback)
 
Used only in **baseline mode**, when no organization standard is declared and no sibling charts
exist to infer one from. Everything here is a recommendation drawn from common Helm and
Kubernetes practice, not an organization rule. Tag findings "(baseline)" and word them as
suggestions.
 
## Contents
 
1. Chart layout
2. Naming
3. Labels and selectors
4. Helpers
5. values.yaml
6. Workload hygiene
7. Documentation
## 1. Chart layout
 
- `Chart.yaml` has `name`, `description`, `version`, and `appVersion`, with `type` set
  deliberately (`application` or `library`).
- One resource per template file, named for the kind and role (`deployment.yaml`,
  `service.yaml`, `configmap-app.yaml`), except tightly coupled resources (a Service and its
  headless twin), which may share a file.
- Shared template logic lives in `templates/_helpers.tpl`. Partials there are namespaced by
  chart name (`mychart.fullname`) to avoid collisions with subcharts.
- `values.schema.json` is present for anything consumed by more than one team, so bad values
  fail at `helm lint` rather than at deploy time.
## 2. Naming
 
- Resource names come from one helper (`fullname`), not hand-built string concatenation in each
  template.
- Names are truncated to 63 characters and `-` trimmed, since many Kubernetes names have that
  limit.
- Template file names and helper names say what they do. `helper1` and `config2.yaml` don't.
## 3. Labels and selectors
 
- Every resource carries the Kubernetes recommended labels: `app.kubernetes.io/name`,
  `app.kubernetes.io/instance`, `app.kubernetes.io/version`, `app.kubernetes.io/managed-by`,
  plus `helm.sh/chart`.
- Labels are generated by a shared helper (`labels`), and selectors by a second, smaller helper
  (`selectorLabels`). Selector labels are a stable subset: never include `version` or chart
  version, since selectors are immutable on Deployments and StatefulSets.
- All resources in the chart use the same label scheme.
## 4. Helpers
 
- Each helper has a one-line comment saying what it returns and where it's used.
- Helpers do one job. A helper that both builds a name *and* decides feature flags is two
  helpers.
- Prefer `include` over `template` (its output can be piped, e.g. into `nindent`).
## 5. values.yaml
 
- Grouped by concern, in a consistent order (image, replicas, service, ingress, resources,
  probes, config, then integrations).
- Every non-obvious key has a comment saying what it does and what units or values are valid.
  Commented-out examples are fine for optional blocks.
- Keys are camelCase or snake_case, one style throughout.
- Defaults render a working chart. Required inputs use `required "message"` with an
  actionable message.
- Deep nesting (more than 3 levels) and flag-per-line sprawl are signs a block should be
  restructured.
- Environment override files (`prod-values.yaml`) contain only what differs, and say so in a
  header comment.
## 6. Workload hygiene (readability-relevant)
 
- `resources` requests and limits are set, or omission is explained in a comment.
- Liveness and readiness probes are present, use named ports, and have visible timing values,
  rather than magic numbers buried in a template.
- Container ports are named (`http`, `grpc`), and Services reference them by name.
- Conditionals (`if .Values.x.enabled`) wrap whole resources or whole blocks, not fragments
  that make the rendered YAML hard to picture.
- Long template expressions are broken across lines, or extracted to a helper. Deeply nested
  `if`/`with`/`range` (three or more levels) is a readability smell.
## 7. Documentation
 
- `README.md` covers what the chart deploys, prerequisites, a minimal install example, and the
  important values.
- `NOTES.txt` describes *this* chart's real post-install steps, or is removed. Unedited
  `helm create` boilerplate is misleading.
- Comments explain *why*, especially for workarounds, ordering constraints, and hooks.
